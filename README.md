# Mini NPU 시뮬레이터

## 1. 프로젝트 개요

코디세이 미션 3으로 개발한 Python 콘솔 애플리케이션이다.

입력 패턴과 필터의 같은 위치에 있는 값을 곱하고 모두 더하는 MAC 연산을 반복문으로 구현했다.

사용자 입력 분석과 JSON 일괄 분석을 지원하며, 점수·판정·성능 표와 결과 리포트를 출력한다.

실제 NPU 하드웨어를 구현하거나 필터를 학습하는 프로그램은 아니다.

## 2. 개발 환경

- 요구 환경: Python 3.8 이상
- 실제 검증 환경: Windows PowerShell, Python 3.12.10
- 외부 라이브러리 사용 없음
- json, pathlib, math, re, time 등 Python 표준 라이브러리 사용
- 자동 검증에는 unittest와 표준 라이브러리 사용
- NumPy, pandas와 벡터화 라이브러리 사용 없음

별도의 pip 설치 명령은 필요하지 않다.

## 3. 기능과 실행 흐름

### 사용자 입력 모드

```text
필터 A 입력
→ 필터 B 입력
→ 저장된 필터 출력·확인
→ 패턴 입력
→ 두 필터의 MAC 계산
→ A/B/판정 불가 출력
→ 3×3 성능 표
→ 메뉴 복귀
```

각 행은 공백으로 구분한 숫자 3개로 입력한다.

숫자 개수와 숫자 변환을 검사하고, 잘못된 행은 안내 후 다시 입력받는다.

정수와 실수를 사용할 수 있으며 NaN과 무한대는 거절한다.

### JSON 분석 모드

```text
필터와 패턴 로드·검증
→ 케이스별 MAC 점수·판정·PASS/FAIL
→ 네 크기의 성능 표
→ 전체 테스트 수·통과 수·실패 수
→ 실패 식별자와 사유 목록
→ 메뉴 복귀
```

원본 data.json은 다음 구조를 사용한다.

- filters: size_5, size_13, size_25
- 각 크기의 필터: cross, x
- patterns: size_N_idx 형태의 식별자
- 각 패턴: input, expected

식별자에서 N을 추출하고 해당 size_N 필터를 선택한다.

행·열 개수, 자료형, 숫자 값과 필수 항목을 검증한 뒤 Matrix로 변환한다.

케이스의 검증·계산 오류는 해당 케이스를 FAIL로 기록하고 다음 케이스를 계속 분석한다.

파일 전체를 읽거나 해석하지 못하면 분석 불가 사유를 안내하고 메뉴로 돌아간다.
이를 정상 분석의 0 FAIL로 표시하지 않는다.

## 4. MAC와 판정 정책

### MAC 계산

N×N의 모든 위치를 중첩 반복문으로 순회한다.

```text
누적값 = 누적값 + 입력값 × 필터값
```

일반적인 행렬 곱셈이 아니라 같은 위치의 곱을 모두 합산하는 연산이다.

Matrix는 특정 행·열의 값 저장과 조회를 제공한다.
필수 크기인 3×3, 5×5, 13×13, 25×25를 검증했다.

### 라벨 정규화

| 원본 표현 | 표준 라벨 |
|---|---|
| expected의 + | Cross |
| 필터 키 cross | Cross |
| expected와 필터 키의 x | X |

앞뒤 공백과 대소문자 차이도 처리한다.
표준 라벨 Cross와 X를 다시 입력해도 같은 표준값을 반환한다.

알 수 없는 라벨, 정규화 후 중복된 필터와 필수 필터 누락은 오류로 처리한다.

### epsilon 동점 처리

```text
epsilon = 1e-9
abs(점수 A - 점수 B) < epsilon이면 동점
```

동점 검사를 먼저 수행하고, 동점이 아니면 높은 점수를 선택한다.
차이가 epsilon과 같으면 동점이 아니다.

| 모드 | 우세 판정 | 동점 표시 |
|---|---|---|
| 사용자 입력 | A 또는 B | 판정 불가 |
| JSON 분석 | Cross 또는 X | UNDECIDED |

사용자 입력의 필터 A가 반드시 십자가라고 가정하지 않는다.

JSON 분석에서는 Cross 점수와 X 점수를 비교하고, 정규화한 expected와 판정이 같으면 PASS, 다르면 FAIL이다.

UNDECIDED는 모양 라벨이 아니라 판정 보류 상태이다.

## 5. 성능 분석

### 측정 방법

- time.perf_counter() 사용
- 필터 하나의 MAC 함수 호출 시간 측정
- 준비 실행 1회는 평균에서 제외
- 이후 크기별 10회 측정한 1회 평균 사용
- 초 단위 측정값에 1000을 곱하여 ms로 변환
- 배열 준비, 파일 읽기, 사용자 입력과 출력 시간 제외
- MAC 함수 내부의 검사와 값 조회 비용은 포함

사용자 입력 모드는 실제 입력 패턴과 필터 A를 측정한다.

JSON 모드의 크기별 비교에는 모든 값이 1.0인 공통 측정용 배열을 사용한다.
이 측정 자료는 원본 판정과 PASS/FAIL 계산에 사용하지 않는다.

### 저장한 실제 측정값

| 크기 | 평균 시간(ms) | 연산 횟수(N^2) | 측정 횟수 |
|---|---:|---:|---:|
| 3×3 | 0.011840 | 9 | 10 |
| 5×5 | 0.028900 | 25 | 10 |
| 13×13 | 0.183770 | 169 | 10 |
| 25×25 | 1.154100 | 625 | 10 |

N^2는 N×N을 뜻하며, 필터 하나를 한 번 적용하는 MAC 횟수이다.

표는 결과 파일 저장 당시의 기록이다.
시간은 실행 환경과 컴퓨터 상태에 따라 달라지며, 같은 숫자의 재현을 보장하지 않는다.

화면과 표에는 소수점 아래 6자리로 표시하고, 결과 파일에는 평균 시간의 원래 반환값을 저장했다.

- 측정 원본: [성능 결과 JSON](docs/08-performance-results.json)
- 측정 설명: [8단계 수행 기록](docs/08-performance.md)

## 6. 실행 방법

main.py와 제공된 data.json을 같은 폴더에 둔다.

터미널에서 main.py가 있는 폴더로 이동하여 실행한다.

```powershell
python main.py
```

| 메뉴 | 동작 |
|---|---|
| 1 | 3×3 사용자 입력 분석 |
| 2 | data.json 일괄 분석 |
| 0 | 종료 |

분석 후에는 메뉴로 돌아간다.
잘못된 메뉴 입력은 안내 후 다시 입력받는다.

data.json의 기본 경로는 현재 작업 위치가 아니라 main.py의 위치를 기준으로 처리한다.

입력 종료 또는 Ctrl+C 발생 시 안내 후 종료한다.

## 8. 결과 리포트

### 원본 데이터 분석 결과

| 케이스 | Cross 점수 | X 점수 | 판정 | 기대값 | 결과 |
|---|---:|---:|---|---|---|
| size_5_1 | 0.9 | 0.8999999999999999 | UNDECIDED | X | FAIL |
| size_5_2 | 8.9 | 0.1 | Cross | Cross | PASS |
| size_13_1 | 0.3 | 14.700000000000008 | X | X | PASS |
| size_13_2 | 7.499999999999997 | 7.5 | UNDECIDED | Cross | FAIL |
| size_25_1 | 4.9 | 4.899999999999999 | UNDECIDED | X | FAIL |
| size_25_2 | 52.9 | 0.1 | Cross | Cross | PASS |

전체 6개, 통과 3개, 실패 3개로 집계가 일치한다.

### 실패 원인과 복잡도 분석

1. 원본 expected의 +와 x를 Cross와 X로 정규화하여 비교했다.
2. 필터 키도 같은 표준 라벨로 통일하여 표현 차이에 따른 잘못된 비교를 방지했다.
3. 두 점수 차이의 절댓값이 1e-9보다 작으면 UNDECIDED로 판정했다.
4. size_5_1은 0.9와 0.8999999999999999의 차이가 epsilon보다 작아 동점이 되었다.
5. size_5_1의 기대값은 X이므로 동점 판정과 일치하지 않아 FAIL이다.
6. size_13_2도 7.499999999999997과 7.5의 차이가 epsilon보다 작고 기대값은 Cross이므로 FAIL이다.
7. size_25_1도 4.9와 4.899999999999999의 차이가 epsilon보다 작고 기대값은 X이므로 FAIL이다.
8. 나머지 세 케이스는 표준 라벨 판정이 기대값과 일치하여 PASS이다.
9. 이번 원본 분석에서는 구조 오류나 계산 불가로 실패한 케이스는 없었다.
10. PASS를 늘리기 위해 원본 데이터나 epsilon을 변경하지 않았다.
11. 필터 하나의 MAC 계산은 N개 행과 각 행의 N개 열을 순회하므로 N²회의 곱셈·누적을 수행한다.
12. 따라서 필터 하나의 시간 복잡도는 O(N²)이며, 두 필터를 적용해도 고정된 상수배이므로 O(N²)이다.
13. 저장한 성능 표에서는 위치 수가 9에서 625로 증가하면서 평균 시간도 증가했다.
14. 실제 시간 비율은 연산 횟수 비율과 정확히 같지 않으며 Python 호출 비용과 실행 환경 등의 영향을 받는다.
15. 입력·출력·파일 읽기·배열 준비는 측정에서 제외했지만 MAC 함수 내부의 검사와 값 조회 비용은 포함했다.
16. 배열 저장 공간은 O(N²)이고 MAC 함수 자체의 누적값·반복 변수 등 추가 공간은 O(1)이다.
17. 자동 검증 62개 통과는 원본의 FAIL이 사라졌다는 뜻이 아니라, 세 FAIL을 포함한 동작이 정책에 맞는지 확인했다는 뜻이다.

## 9. 재현 방법

### 사용자 입력 모드

프로그램을 실행하고 메뉴 1을 선택한다.

필터 A에 다음 세 행을 한 줄씩 입력한다.

```text
0 1 0
1 1 1
0 1 0
```

필터 B에 다음 세 행을 입력한다.

```text
1 0 1
0 1 0
1 0 1
```

저장된 필터를 확인한 뒤, 패턴에 다음 세 행을 입력한다.

```text
0 1 0
1 1 1
0 1 0
```

예상 결과:

```text
필터 A MAC 점수: 5
필터 B MAC 점수: 1
판정 결과: A
```

이어서 실제 입력 패턴과 필터 A의 3×3 성능 표가 출력되고 메뉴로 돌아간다.

같은 필터에서 X 패턴을 입력하면 점수 1과 5, 판정 B이다.
모두 0인 패턴을 입력하면 점수 0과 0, 판정 불가이다.

### JSON 분석 모드

메뉴 2를 선택한다.

케이스별 결과, 네 크기의 성능 표, 전체 요약과 실패 목록이 순서대로 출력된다.

원본 기준 예상 집계:

```text
전체 테스트 수: 6
통과 수: 3
실패 수: 3
```

실패 목록은 size_5_1, size_13_2, size_25_1이다.

### 의도적 오류 검증

사용자 입력에서 숫자 부족·초과, 문자와 빈 입력을 넣으면 해당 행을 다시 입력받아야 한다.

JSON 오류 검증은 원본을 보존하고 별도 시험용 자료로 수행한다.
자동 검증에는 크기 불일치, 누락 항목, 라벨 오류, 파일 오류와 다음 케이스 계속 처리를 포함했다.

## 11. 구현의 한계

- 실제 NPU의 병렬 처리 성능을 재현하지 않는다.
- 필터를 자동으로 학습하지 않는다.
- MAC 점수는 확률이나 일반적인 그림 유사도 지표가 아니다.
- 위치별 점수 비교이므로 이동·회전·잡음에 대한 일반적인 인식을 보장하지 않는다.
- 절대 허용오차 정책에 따라 기대값과 다른 동점 판정이 나올 수 있다.
- 짧은 실행 시간은 환경 영향을 받으므로 단일 측정만으로 성능을 일반화하지 않는다.

## 추가 분석: 대규모 MAC 처리와 CPU·NPU 병목

### 1. 분석 범위

현재 프로그램은 Python 반복문으로 MAC 원리를 학습하는 시뮬레이터이다.
실제로 검증하고 시간을 기록한 크기는 3×3, 5×5, 13×13, 25×25이다.
아래 1000×1000 이상의 분석은 연산량과 자료 구조에 근거한 예상이며,
해당 크기를 실행해 측정한 결과나 실제 NPU의 측정 결과는 아니다.

### 2. N이 1000 이상일 때의 시간 영향

필터 하나의 MAC 계산은 N²개 위치의 곱셈과 누적을 수행한다.
1000×1000에서는 필터 하나당 1,000,000회, 두 필터는 2,000,000회의
MAC이 필요하다. MAC 1회는 곱셈과 누적 덧셈을 한 쌍으로 센 것이다.

25×25의 625회와 비교하면 1000×1000의 위치 수는 1,600배이다.
N을 두 배로 늘리면 위치 수는 네 배가 된다.
다만 실제 시간은 캐시, 메모리 접근, Python 실행 비용의 영향을 받으므로
기존 측정 시간에 1,600을 곱한 값을 실측 시간으로 사용할 수는 없다.

현재 구현에서는 반복문 외에도 값 조회와 유효성 검사에 시간이 들어간다.
동일한 입력과 여러 필터를 반복 계산하면 이 비용도 누적된다.
입력 검증은 유지하되, 이미 검증한 자료를 계산할 때 중복 검사를 줄일 수 있는지
먼저 성능을 측정하고 검토할 필요가 있다.

### 3. 메모리 부담과 메모리 레이아웃

1000×1000 배열은 원소가 1,000,000개이다.
모든 원소를 8바이트 숫자로 연속 저장한다고 가정하면
배열 하나의 숫자 저장 공간은 약 8MB, 입력과 필터 두 개는 약 24MB이다.
이는 객체 관리 비용 등을 제외한 비교용 계산이다.

현재 Python의 중첩 리스트는 연속된 8바이트 숫자 배열과 다르다.
리스트의 참조, 행별 리스트와 숫자 객체 등에 추가 공간이 필요하며,
실제 메모리 사용량은 자료의 생성 방식과 Python 환경에 따라 달라진다.
JSON 로드와 Matrix 변환 과정에서 원본 자료와 변환된 자료가 함께 존재하면
최대 메모리 사용량은 더 커질 수 있다.

현재와 같이 행을 바깥 반복문으로 순회하고 열을 안쪽에서 순회하면
각 행의 원소를 순서대로 읽는다.
큰 배열에서는 행 우선의 연속적인 메모리 배치와 순차 접근을 사용하면
캐시 활용과 메모리 접근 효율을 개선할 수 있다.
표준 라이브러리 array 모듈의 평탄한 숫자 배열도 검토할 수 있지만,
자료형 범위와 기존 정수·실수 처리 규칙을 먼저 확인해야 한다.

### 4. 우선 적용할 최적화 순서

첫째, 파일 읽기·변환 시간과 MAC 시간을 분리하여 병목을 측정한다.
메모리도 파일 크기만으로 판단하지 않고 실행 중 사용량을 확인한다.

둘째, 검증된 배열을 재사용하고 불필요한 복사와 중간 자료 생성을 줄인다.
반복 계산에 필요한 자료만 보관하고 사용이 끝난 자료는 해제한다.

셋째, 메모리 레이아웃과 접근 순서를 개선한다.
행을 지역 변수로 참조하는 방식이나 연속적인 숫자 저장 구조를 검토한다.
최적화 전후의 점수와 epsilon 판정이 유지되는지 함께 확인한다.

넷째, 자료가 메모리나 캐시에 부담을 주면 블록 처리를 검토한다.
전체 배열을 작은 행 묶음이나 타일로 나누어 부분 MAC 합을 계산하고 합친다.
블록 크기는 캐시와 메모리 제약을 고려하여 측정으로 선택한다.
다만 현재처럼 전체 JSON과 Matrix를 먼저 메모리에 올린 후 나누기만 하면
원본 보관에 필요한 메모리는 줄지 않는다.
메모리 절감에는 읽기·변환 단계까지 블록 단위로 처리하는 설계가 필요하다.

다섯째, RAM보다 큰 자료를 반복 사용한다면 메모리 매핑을 검토한다.
표준 라이브러리 mmap은 파일 일부를 메모리처럼 접근하도록 돕지만,
JSON 숫자 배열을 자동으로 계산용 숫자 배열로 바꾸지는 않는다.
직접적인 숫자 접근에는 고정 길이 바이너리 형식 등 저장 구조의 변경이 필요하다.
디스크 입출력과 페이지 폴트가 발생하면 오히려 느려질 수도 있다.

마지막으로 독립적인 패턴이나 블록의 병렬 처리를 검토한다.
일반적인 CPython에서는 GIL 때문에 순수 Python 계산을 스레드로 나누는 것만으로
CPU 계산 속도 향상을 기대하기 어렵다.
표준 라이브러리 multiprocessing을 사용할 수 있지만,
프로세스 생성, 자료 전달·복사, 결과 합산 비용과 메모리 증가를 고려해야 한다.
작은 자료는 직렬 실행이 더 빠를 수 있으므로 먼저 비교 측정해야 한다.

이 내용은 개선 설계이며 현재 제출 코드에 모두 구현한 것은 아니다.
외부 라이브러리 없이 반복문으로 MAC을 구현한다는 과제 조건을 유지한다.

### 5. CPU와 NPU의 처리 특성 비교

| 구분 | 현재 Python CPU 구현 | 일반적인 NPU 처리 |
|---|---|---|
| 계산 방식 | Python 반복문으로 위치를 차례로 계산 | 다수의 연산 장치로 MAC을 병렬 수행 |
| 주요 비용 | 해석기 실행, 값 조회, 검사, 메모리 접근 | 데이터 전달, 메모리 대역폭, 장치 활용률 |
| 적합한 작업 | 작은 자료, 분기와 제어가 많은 작업 | 지원되는 연산으로 구성된 대규모 반복 계산 |
| 준비 비용 | 현재 자료로 바로 함수 호출 | 자료 변환·전송·실행 준비 등이 필요 |
| 제약 | Python 수준의 반복 실행 비용 | 장치별 연산·자료형·메모리 지원 제약 |

CPU 자체가 언제나 직렬로만 작동하는 것은 아니다.
CPU도 다중 코어와 SIMD 등을 지원하지만, 현재 코드는 이를 직접 활용하는
고성능 병렬 구현이 아니라 Python 반복문 기반 구현이다.
NPU의 실제 실행 방식과 지원 연산은 장치마다 다르다.

### 6. 대규모 MAC에서 발생할 수 있는 병목

현재 CPU 구현에서는 반복 횟수가 늘면서 Python 실행 비용이 커진다.
더 효율적인 계산 구현으로 바꾸면 계산 자체보다 메모리에서 자료를 가져오는
속도가 병목이 될 수도 있다.

NPU도 병렬 연산 장치가 많다는 이유만으로 항상 빠르지는 않다.
작은 패턴을 한 개씩 전송하면 계산보다 전송과 실행 준비 시간이 길어질 수 있다.
필터와 입력이 장치 내부 메모리에 들어가지 않으면 외부 메모리 접근이 반복되고,
메모리 대역폭이 연산 장치에 필요한 데이터를 공급하지 못할 수 있다.

또한 처리할 작업이 너무 적으면 병렬 연산 장치가 충분히 활용되지 않는다.
지원되지 않는 연산이 CPU로 되돌아가면 CPU·NPU 사이의 이동과 동기화가 증가한다.
반복 단계가 서로의 결과를 기다리는 구조라면 병렬화 효과도 제한된다.

### 7. CPU·NPU 오프로드 전략

오프로드는 계산의 일부를 CPU에서 가속 장치로 넘기는 것이다.
판단 기준은 MAC 계산 시간만이 아니라 자료 변환·전송·대기·계산·결과 회수까지
포함한 전체 실행 시간이어야 한다.

입력 검증, JSON 읽기와 오류 안내 등 제어 작업은 CPU에서 처리하고,
지원되는 대규모 MAC 묶음은 NPU로 보내는 구성을 검토할 수 있다.
여러 패턴을 배치로 묶고 같은 필터를 장치에 재사용하면 전송 비용을 나눌 수 있다.
장치 메모리가 부족하면 블록으로 나누되 블록 사이의 전송 비용을 함께 측정한다.
장치가 지원하는 경우 전송과 계산을 겹치는 방법도 검토할 수 있다.

자료형 변환이나 양자화를 사용하면 속도와 메모리 면에서 이점이 있을 수 있지만,
점수의 정밀도가 달라져 epsilon 기반 판정이 바뀔 수 있으므로 별도 검증이 필요하다.
병렬 부분합도 덧셈 순서를 바꾸므로 부동소수점 결과가 달라질 수 있다.

작은 입력은 CPU에서 처리하고, 충분히 큰 작업만 가속 장치로 넘기는 기준은
실제 장치의 전체 실행 시간을 비교하여 정해야 한다.
현재 제출물은 실제 NPU 오프로드를 구현하지 않았으며,
이 절은 대규모 처리 시 고려할 설계 전략을 설명한다.
